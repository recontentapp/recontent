# Why Recontent

Recontent turns your tokens and components into a design system that people, agents and CI can read.

## The problem

A design system's decisions end up copied into many places. Colors, spacing and type live in a CSS
file, a Tailwind config, a constants module, a Figma library and a docs page. The API of your components
lives in their source and in a documentation site that nobody updates. Each copy drifts. Renaming a
token or a prop means hunting for every place that mentions it, and nothing tells you which change will
break a consumer.

Coding agents make it worse. They write UI from memory: they invent prop names, pass values a component
does not accept and hard-code a hex value where a token exists. Nobody notices until review.

## Four pillars

**Tokens: typed layers and themes.** Your decisions live in one typed file, `recontent.config.ts`, and
everything else is generated: CSS variables, a Tailwind theme, vanilla-extract or StyleX variables,
TypeScript constants, DTCG files. Mistakes (a missing color step, an override of a token that does not
exist, an alias of the wrong type) fail in the editor or at `recontent build`, not in production.

**Components: introspected from your own TypeScript.** Point Recontent at your components and it reads
their props, defaults and types. You document them with JSDoc where they live (`@usage`, `@example`,
`@category`, `@deprecated`), and the documentation reaches every output. See
[Introspecting components](/guides/introspecting-components) and
[Documenting components](/guides/documenting-components).

**Agents: the exact API, on demand.** [`recontent inspect`](/cli/inspect) gives agents the real props,
tokens and usage notes, in small answers with recoverable errors, so they stop guessing.
[`DESIGN.md`](/plugins/design-md) is loaded up front, and `--from` works for apps that install your design
system from npm. See [Coding with agents](/guides/agents).

**Guardrails: breaking changes are caught.** [`recontent diff`](/guides/diffs) reports a breaking change
to a token or to a prop, and `recontent build --check` keeps generated files honest. Both exit with a code CI understands.

## Layers and themes

Tokens live in three layers (reference, system and components) and themes override values without
touching component code. See [Defining tokens](/guides/defining-tokens) and
[Working with themes](/guides/working-with-themes).

## Aligned with DTCG

Token types and value shapes follow the [Design Tokens Community Group format](https://www.designtokens.org/),
so Recontent stays interoperable: the [DTCG plugin](/plugins/dtcg) exports `.tokens.json` files for
Figma and Tokens Studio, and [`recontent init --dtcg`](/cli/init#importing-dtcg-tokens) starts from
files you already have.

## Who it is for

- Engineers who maintain a design system and want a single, reviewable source of truth.
- Designers who work with tokens and need exports their tools understand.
- Teams whose engineers use coding agents to write UI.
- Teams starting a design system, who can begin from a preset instead of an empty file.
