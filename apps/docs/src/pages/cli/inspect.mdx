# inspect

Prints what `recontent.config.ts` defines: its tokens, its components when
[`introspection`](/tokens/configuration#introspection) is configured, and the git state they were read
from.

```bash
recontent inspect [--format <format>]
recontent inspect tokens [path...] [--type <type>] [--theme <theme>] [--deprecated] [--format <format>]
recontent inspect components [name...] [--deprecated] [--format <format>]
```

Uses the [global options](/cli#global-options) `-c`, `--cwd` and `--log-level`.

## Browsing

Start with the overview, then drill down. Each step prints more about less, so you never have to read
a whole design system to find one token.

```bash
recontent inspect                      # counts per layer and type, themes, component names, git
recontent inspect tokens               # one row per group, with counts
recontent inspect tokens system.color  # the tokens at or under system.color, with values and CSS variables
recontent inspect components           # one line per component
recontent inspect components Button    # its props: type or allowed values, default, required, notes
```

Every overview ends with a `Next:` line that names a command to try.

| Command                        | Without arguments         | With arguments                                                                       |
| ------------------------------ | ------------------------- | ------------------------------------------------------------------------------------ |
| `inspect`                      | The overview.             | None.                                                                                |
| `inspect tokens [path...]`     | Token groups with counts. | Each path is an exact token or a group: `system.color` includes everything under it. |
| `inspect components [name...]` | One line per component.   | Each name is a component or a family: `Tabs` includes `Tabs.Item`.                   |

Options for `tokens`:

| Option            | Description                                                                            |
| ----------------- | -------------------------------------------------------------------------------------- |
| `--type <type>`   | Only tokens of this type, such as `color` or `dimension`.                              |
| `--theme <theme>` | Show only this theme's column next to the default value. An unknown theme is an error. |
| `--deprecated`    | Only deprecated tokens.                                                                |

`components` takes `--deprecated` too. A filter that matches nothing prints an empty result and exits
`0`.

A token is printed with its path, type, value, CSS variable and notes (alias, description,
deprecation), and its value in each theme that overrides it. A component is printed with its source
location, which links to the repository when `origin` is a GitHub, GitLab or Bitbucket remote, and a
table of its **own** props. Props inherited from outside the project, such as the 260 attributes of
`ButtonHTMLAttributes`, are summarized on an `Also accepts:` line instead of listed.

## For agents

The output is plain markdown, which coding agents read well, and it is designed to be used without
reading source:

- identifiers are printed exactly as they are used: token paths, CSS variables, component and prop names;
- the drill-down keeps each answer small, so an agent can ask for `system.color` or `Select` and nothing else;
- an unknown path or name exits `1` and suggests the closest matches on stderr, so a typo is
  recoverable:

  ```text
  error: No token or group matches "system.colr". Did you mean `system.color`?
  ```

`recontent --help` lists the command, and `recontent inspect --help` explains the drill-down.

## For scripts

`--format json` prints one JSON document with the **full detail of the whole selection**, never a
summary, so `recontent inspect tokens --format json` is every token.

| Command              | Document                                                                                                                                                                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `inspect`            | `{ schemaVersion, kind: "overview", config, tokens: { total, layers }, themes, components?, git? }`                                                                                                  |
| `inspect tokens`     | `{ schemaVersion, kind: "tokens", tokens }`, each token with `layer`, `path`, `name`, `type`, `alias?`, `description?`, `deprecated?`, `cssVar` and `values` (`default` plus the themes that differ) |
| `inspect components` | `{ schemaVersion, kind: "components", components, git? }`, each component as described in the [plugin API](/plugin-api#componentmanifest)                                                            |

`schemaVersion` is `"1"` and only changes with a breaking change to these documents.

- **stdout** carries the result and nothing else. Logs and warnings, such as an introspection warning,
  go to stderr.
- Exit code `0` is success, including an empty result from `--type`, `--deprecated` or an empty
  project. Exit code `1` is an error: a path or name that matches nothing, an unknown `--theme`,
  broken token aliases, an introspection failure, or `inspect components` in a config without an
  `introspection` block.

```bash
# Fail CI when a deprecated component is still exported
test "$(recontent inspect components --deprecated --format json | jq '.components | length')" = 0
```

## Cost

`inspect tokens` only loads the config, so it is instant, and keeps working when `introspection` is
misconfigured. `inspect` and `inspect components` build a TypeScript program from the configured
entry, which takes about two seconds for 50 components. Run with `--log-level debug` to see
the timings.
